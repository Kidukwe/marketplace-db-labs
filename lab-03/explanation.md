# Разбор лабораторной №3

Этот файл читается рядом с `queries.sql` и `views.sql`: номера Q01–Q11 совпадают.
Таблицы уже есть из ЛР1; данные берём из ЛР2 и прежних упражнений. Повторять создание таблиц для ЛР3 не требуется.

## Q01. Товар, категория и продавец

**Задача:** вместо непонятных номеров категории и продавца вывести их названия рядом с товаром.

В `products.category_id` хранится ссылка на `categories.id`, в `products.seller_id` — на `sellers.id`. Первичный ключ обозначает саму строку, внешний ключ указывает на строку другой таблицы.

- `FROM public.products AS p` задаёт исходные товары и сокращает имя таблицы до `p`.
- `JOIN sellers s ON p.seller_id = s.id` находит магазин каждого товара.
- Второй `JOIN` находит категорию по `p.category_id = c.id`.
- `SELECT` выводит `p.title`, `c.name`, `s.store_name`; `AS category` и `AS seller` задают названия столбцов результата.
- `ORDER BY p.id` делает порядок воспроизводимым.

У каждой ссылки здесь единственное соответствие, поскольку справа первичный ключ. Поэтому каждый товар даёт одну строку. В схеме внешние ключи обязательны, так что корректные товары не теряются при INNER JOIN. В общем случае INNER JOIN отбрасывает строки без соответствия.

**Для защиты:** «Соединяю три таблицы по внешним и первичным ключам, чтобы получить понятный каталог».

## Q02. Товары без отзывов

**Задача:** найти товары, которые ещё никто не оценил.

`LEFT JOIN reviews r ON p.id = r.product_id` сохраняет товары независимо от наличия отзывов. Если отзывов несколько, появится несколько строк. Если отзывов нет, остаётся одна строка товара с NULL во всех столбцах `r`.

`WHERE r.id IS NULL` оставляет только второй случай. В настоящем отзыве `id` — первичный ключ и NULL быть не может. Проверять `r.comment IS NULL` было бы ошибкой: существующий отзыв тоже может не содержать комментария.

Пример результата соединения до WHERE:

| p.id | p.title | r.id |
|---|---|---|
| 10 | Телефон | 7 |
| 10 | Телефон | 8 |
| 11 | Книга | NULL |

После фильтра остаётся только книга. `p.id IS NULL` не подходит: товар сохранён слева и его id известен. Используется `IS NULL`, а не `= NULL`.

**Для защиты:** «Сохраняю все товары левым соединением, затем выбираю отсутствие строки справа».

## Q03. Количество и средняя цена по каждой категории

**Задача:** получить одну строку отчёта на категорию, в том числе пустую.

Начинаем с `categories`, присоединяем товары через LEFT JOIN. `GROUP BY c.id, c.name` объединяет строки одной категории. `COUNT(p.id)` считает реальные товары, `AVG(p.price)` — среднюю цену, `ROUND(..., 2)` округляет её для показа.

Почему не COUNT(*)? Для пустой категории LEFT JOIN оставляет одну строку с NULL вместо товара. COUNT(*) посчитал бы её как 1; COUNT(p.id) пропустит NULL и вернёт 0. AVG тоже пропускает NULL: у пустой категории среднее равно NULL. Нулевая средняя означала бы бесплатные товары, поэтому не заменяем её нулём.

Почему две колонки группировки? `id` обозначает категорию, `name` позволяет вывести её название явно. PostgreSQL умеет учитывать зависимость остальных полей от первичного ключа, но явное перечисление здесь проще для чтения и защиты.

Сортировка — отдельный шаг: `ORDER BY products_count DESC, c.id`. DESC означает убывание и не пишется внутри GROUP BY. При равных количествах id фиксирует порядок.

**Отличие от написанного вместе запроса:** INNER JOIN показывал только категории с товарами. LEFT JOIN позволяет показать все категории, как требует формулировка «по каждой категории».

## Q04. HAVING

**Задача:** оставить категории, где больше 100 товаров.

После `GROUP BY` уже известны количества в каждой группе. `HAVING COUNT(*) > 100` проверяет это количество; в этом запросе INNER JOIN, поэтому каждая строка группы является реальным товаром и COUNT(*) подходит.

`WHERE` проверяет отдельные строки до группировки. Он подходит, например, для `p.is_active`, но не для результата COUNT по группе. `HAVING` проверяет группы после группировки.

В PostgreSQL нельзя написать `HAVING products_count > 100`, потому что выходное имя из SELECT здесь не разрешено. Нужно повторить `COUNT(*)`. В `ORDER BY products_count DESC` псевдоним разрешён правилами SQL PostgreSQL.

На твоих скриншотах до и после HAVING было семь строк: количества 506, 500 и по 240. Все больше 100, поэтому фильтр ничего не убрал. Для наглядной проверки можно временно поставить порог 300.

## Q05. Скалярный подзапрос

**Задача:** показать товары дороже общей средней цены.

Внутренний запрос `SELECT AVG(p2.price) FROM products p2` возвращает одно значение. Внешний `WHERE p.price > (...)` сравнивает с ним каждый товар. `p2` — отдельный источник строк, он нужен, чтобы среднее вычислялось по всей таблице.

Это некоррелированный подзапрос: он не обращается к строке `p` внешнего запроса. `AS avg_price` допустим, но не обязателен: наружу используется само значение, а не это имя.

Не следует писать внутри `AVG(p.price)`: это ссылка на внешний источник и меняет смысл запроса. Нужна `p2.price`. GROUP BY внутри не нужен, иначе получится несколько средних, которые уже нельзя сравнивать как одно скалярное значение.

## Q06. IN с подзапросом

**Задача:** выбрать товары из категорий, чьи названия начинаются на `ЛР2:`.

Разбираем изнутри:

```sql
SELECT c.id
FROM public.categories AS c
WHERE c.name LIKE 'ЛР2:%'
```

Получаем набор идентификаторов категорий. `LIKE` проверяет шаблон: `ЛР2:` — обязательное начало, `%` — любое продолжение, включая пустое.

Снаружи проверяем `p.category_id IN (...)`: входит ли категория товара в полученный набор? Если внутри вернулись 4, 5 и 6, это по смыслу проверка `IN (4, 5, 6)`, но реальные номера берутся из базы автоматически.

Нужно выбирать `c.id`, а не `c.name`: сравниваем именно номера категорий. Подзапрос IN здесь возвращает один столбец и может вернуть много строк. Пустая корневая категория тоже может попасть в набор, но товаров в ней нет — лишних строк это не добавит.

**Разница с Q05:** Q05 возвращает одно число, Q06 — набор чисел.

## Q07. Коррелированный EXISTS

**Задача:** показать продавцов, у которых есть хотя бы один товар.

Внешний источник — `sellers s`. В подзапросе `WHERE p.seller_id = s.id` есть ссылка на внешнего продавца. Это делает подзапрос коррелированным: проверка зависит от текущей строки продавца.

`EXISTS` отвечает только на вопрос «есть хотя бы одна подходящая строка?». `SELECT 1` — условная константа, её значение не важно. Это не количество товаров и не номер продавца. Продавец появляется один раз, даже если у него тысяча товаров.

Логически проверяем каждого продавца; это не обещание буквального запуска отдельного запроса на каждую строку: планировщик может преобразовать выполнение.

**Отличие от JOIN:** JOIN возвращает пары строк и может повторять продавца. EXISTS только проверяет наличие связи.

## Q08. Обычный CTE и оплаченные продажи

**Задача:** разложить аналитику продаж на понятные шаги.

1. `paid_items` получает позиции заказов и номера продавцов товаров. EXISTS оставляет только позиции заказов, у которых есть `payments.status = 'completed'`.
2. `seller_totals` группирует эти позиции по продавцу. `COUNT(DISTINCT order_id)` считает заказы без повторов, `SUM(quantity)` — проданные единицы, `SUM(quantity * unit_price)` — сумму позиций.
3. Основной SELECT добавляет название магазина и сортирует по сумме продаж.

Берём `order_items.unit_price`, потому что это цена во время покупки. Текущая `products.price` может измениться; замена исторической цены текущей исказила бы старые продажи.

Сумма здесь означает стоимость позиций заказов с завершённым платежом. Это явно выбранное учебное правило, а не бухгалтерский расчёт прибыли: себестоимость, комиссии, частичные возвраты и доставка в формулу не входят. `pending`, `failed`, `refunded` не учитываются. Оригинальный заказ ЛР1 имеет статус заказа pending, но завершённый платёж: по выбранному правилу такой платёж учитывается.

CTE существует только внутри одного SQL-оператора и не создаёт постоянную таблицу. Он улучшает читаемость. Он не обязан быть отдельной физической временной таблицей: планировщик PostgreSQL может встроить его в общий план.

## Q09. Рекурсивный CTE категорий

**Задача:** пройти иерархию на любую глубину, а не вручную соединять таблицу по одному разу на каждый уровень.

- Начальная часть выбирает корни: `parent_id IS NULL`. Их глубина равна 0, путь состоит из одного id и названия.
- `UNION ALL` добавляет строки рекурсивной части.
- Рекурсивная часть соединяет `child.parent_id = tree.id`: ищет детей найденных категорий.
- `depth + 1` увеличивает глубину, `category_path` дописывает название, `path_ids` — идентификатор.
- Когда новых детей нет, обход заканчивается.

Пример: `Каталог` → `Электроника` → `Смартфоны` даёт глубины 0, 1, 2.

`WHERE NOT (child.id = ANY(tree.path_ids))` запрещает повторно посетить id в текущем пути. В схеме CHECK запрещает ссылку категории на себя, но сам по себе не запрещает цикл из нескольких категорий. Массив пути защищает рекурсию от повторного посещения. Обход начинается от корней; замкнутый цикл без корня в результат не попадёт. Этот запрос показывает лес корректных иерархий, а не является полной диагностикой повреждённых циклов.

Для одного дерева добавь в начальную часть `AND c.name = 'ЛР2: Каталог'`. Не нужно подставлять случайный id из чужого окружения. При сортировке по массиву path_ids потомки идут рядом со своим предком.

## V01 и Q10. Представление каталога

`CREATE OR REPLACE VIEW public.lr3_product_catalog AS SELECT ...` сохраняет запрос Q01 с дополнительными полями цены и активности под именем. Данные в обычном VIEW не копируются.

Q10 обращается к нему почти как к таблице: фильтрует активные товары и выводит двадцать самых дорогих. Сортировка указана в запросе к VIEW: само представление не обещает порядок строк.

`OR REPLACE` позволяет повторить установку того же определения без удаления таблиц. Файл обновляет только два представления с именами ЛР3. Он не заменяет исходные таблицы.

## V02 и Q11. Представление отчёта по продавцам

**Задача:** показывать всех продавцов, включая магазины с нулём товаров или продаж.

`product_totals` отдельно считает товары продавца. `paid_sales` отдельно считает позиции оплаченных заказов. Затем оба результата присоединяются к `sellers` через LEFT JOIN. `COALESCE(..., 0)` заменяет отсутствующие количества и суммы нулём.

Почему нельзя просто соединить sellers → products → order_items и посчитать COUNT(*) как товары? Один товар, заказанный десять раз, породит десять строк. Мы получили бы число позиций, а не товаров. Предварительные независимые агрегации дают одну строку на продавца и предотвращают это размножение.

Два товара одного продавца в одном заказе дают два элемента quantity, но один `paid_orders_count`, поэтому используется COUNT(DISTINCT order_id). Один заказ с товарами разных продавцов может учитываться по одному разу у каждого: сумма числа заказов по продавцам не всегда равна числу уникальных заказов магазина целиком.

Q11 читает готовые показатели без повторного написания аналитики. VIEW показывает актуальные данные при каждом новом запросе в рамках обычных правил видимости транзакций.

## Что делать после чтения

Открой all.sql, выполни целиком и просмотри вкладки результатов. Для самопроверки объясни цепочку: какие строки берём → как соединяем → что группируем → что фильтруем → какие поля выводим. Конспект обучения хранится отдельно; наличие готового запроса ещё не означает, что тема освоена без подсказки.
