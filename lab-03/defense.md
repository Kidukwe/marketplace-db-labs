# Подготовка к защите ЛР3

Вопросы соответствуют разделу методички на с. 26. Примеры берутся из текущей работы.

## 1. Что такое соединение таблиц и по какому условию выполняется?

JOIN формирует связанные пары строк таблиц по условию ON. Обычно сравнивают внешний ключ с первичным: `p.category_id = c.id`. В Q01 так получаем товар, категорию и продавца. Одинаковые имена столбцов сами по себе связь не задают.

## 2. Чем INNER JOIN отличается от LEFT JOIN?

INNER JOIN оставляет только совпавшие пары. LEFT JOIN также сохраняет строки слева без совпадений, подставляя NULL справа. Q02 использует LEFT JOIN и `r.id IS NULL`, чтобы найти товары без отзывов. Если бы использовали INNER JOIN, такие товары исчезли бы ещё до WHERE.

## 3. Какие агрегатные функции известны? COUNT(*) и COUNT(столбец)?

COUNT считает, SUM суммирует, AVG вычисляет среднее, MIN/MAX находят минимум/максимум. COUNT(*) считает все строки, COUNT(столбец) — строки, где этот столбец не NULL. В Q03 COUNT(p.id) возвращает 0 для пустой категории, а COUNT(*) ошибочно дал бы 1 после LEFT JOIN. AVG игнорирует NULL; для пустой группы присоединённых товаров получается NULL, а не ноль.

## 4. Для чего GROUP BY и что допустимо выводить?

GROUP BY объединяет строки с одинаковыми ключами в группы, каждая даёт одну строку результата. Выводим ключи группировки и агрегатные выражения; PostgreSQL также допускает некоторые функционально зависимые поля, например остальные поля таблицы при группировке по её первичному ключу. В нашей работе для ясности явно пишем `GROUP BY c.id, c.name`.

## 5. WHERE и HAVING: в чём различие и порядок?

WHERE фильтрует строки до группировки, HAVING — уже сформированные группы. Например, `WHERE p.is_active` оставляет активные товары, `HAVING COUNT(*) > 100` оставляет большие категории.

Удобная логическая последовательность для этих запросов: FROM/JOIN → WHERE → GROUP BY/агрегаты → HAVING → SELECT → ORDER BY → LIMIT. Это модель смысла, а не требование к физическому плану выполнения. В PostgreSQL выходной псевдоним SELECT доступен в ORDER BY, но не в HAVING.

## 6. Что такое подзапрос? Коррелированный и некоррелированный?

Подзапрос — SELECT внутри другого запроса. Некоррелированный не зависит от внешней строки: Q05 вычисляет общую AVG по p2. Коррелированный обращается к внешнему источнику: Q07 использует `p.seller_id = s.id`. Не нужно утверждать, что коррелированный вариант всегда медленнее: это зависит от плана, данных и индексов.

Скалярный подзапрос должен вернуть один столбец и не более одной строки; при нуле строк его результат NULL, при нескольких строках — ошибка. Наш AVG без GROUP BY возвращает одну строку, даже если таблица пуста (значение AVG будет NULL).

## 7. Как работает EXISTS и когда нужен?

EXISTS истинен, если подзапрос вернул хотя бы одну строку. Удобен для «есть ли товары у продавца?» или «есть ли завершённый платёж у заказа?». Значение `SELECT 1` не важно; EXISTS не считает все строки для вывода. Внешняя строка не размножается от нескольких совпадений. NOT EXISTS проверяет отсутствие совпадений.

## 8. Что такое CTE и зачем рекурсивный?

WITH задаёт именованный промежуточный результат на время одного оператора. Q08 делит аналитику на оплаченные позиции и итог по продавцам. WITH RECURSIVE позволяет использовать результат предыдущих итераций: Q09 начинает с корней и последовательно находит детей. Окончание — когда рекурсивная часть не находит новых строк. Массив посещённых id не даёт повторно войти в тот же узел текущего пути.

## 9. Что такое VIEW? Хранит ли данные?

Обычный VIEW — сохранённое определение SELECT, а не копия строк. Запрос к нему вычисляет результат по актуальным видимым данным таблиц. В работе есть каталог `lr3_product_catalog` и отчёт `lr3_seller_report`. Они упрощают запросы к часто нужным данным.

VIEW может быть частью ограничения доступа к столбцам, но само его создание не меняет права пользователя. В этой лабораторной GRANT/REVOKE не настраиваются.

## 10. Чем отличается материализованное представление?

MATERIALIZED VIEW физически хранит результат. Чтение может быть быстрее, но данные не обновляются автоматически вслед за таблицами: нужен REFRESH MATERIALIZED VIEW. Обычный VIEW не хранит отдельный результат и не требует REFRESH. По ТЗ создаём два обычных VIEW; материализованное объясняем теоретически.

## Дополнительные вопросы по реализации

**Почему сумма продаж считается по unit_price?** Это цена в позиции заказа на момент покупки; текущая цена товара могла измениться.

**Какие продажи учитываются?** Позиции заказов с платежом completed. Это выбранное учебное правило; статусы заказа и платежа — разные поля.

**Почему COUNT(DISTINCT order_id)?** В одном заказе может быть несколько товаров одного продавца; заказ нужно посчитать один раз для этого продавца.

**Зачем предварительно агрегировать товары и продажи?** Чтобы несколько заказов одного товара не увеличили products_count.

**Почему после HAVING у меня те же строки?** Все показанные категории имели более 100 товаров. Фильтр корректен, но не исключает ни одну из них.

**Почему Q03 показывает больше категорий, чем Q04?** Q03 сохраняет пустые категории левым соединением. Q04 рассматривает категории с товарами и дополнительно фильтрует количество.

**Почему у меня другие числа, чем в отчёте проверки?** Тестовая база содержит только воспроизводимые seed ЛР1–ЛР2; у тебя есть дополнительные товары из ручных упражнений. SQL не привязан к конкретным id или количествам.
