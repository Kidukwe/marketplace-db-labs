# Разбор четвёртой лабораторной

## Общая идея

GROUP BY заменяет множество исходных строк одной строкой на группу. Оконная функция добавляет расчёт к каждой строке, сохраняя детали.

Например, у категории есть товары с ценами 100, 100 и 50. GROUP BY вернёт одну среднюю 83,333…, а AVG(price) OVER (PARTITION BY category_id) оставит три товара и добавит эту среднюю каждому.

OVER описывает, какие строки участвуют в расчёте. PARTITION BY отделяет категории друг от друга. ORDER BY внутри OVER задаёт последовательность расчёта. ORDER BY в конце всего SELECT сортирует вывод — это разные задачи.

## Q01 Рейтинг товаров внутри категории

ROW_NUMBER присваивает отдельный номер каждому товару. Порядок `price DESC, id` делает результат однозначным при равных ценах. Нумерация начинается заново в каждой категории из-за PARTITION BY.

RANK и DENSE_RANK используют именованное окно w с порядком только по price DESC. Товары с равными ценами считаются равными по рейтингу.

| Цена | ROW_NUMBER при порядке по id | RANK | DENSE_RANK |
|---:|---:|---:|---:|
| 100 | 1 | 1 | 1 |
| 100 | 2 | 1 | 1 |
| 50 | 3 | 3 | 2 |

RANK пропускает место после ничьей, DENSE_RANK — нет. Если добавить id в окно RANK, равенство исчезнет: пары (100, id1) и (100, id2) различаются. Поэтому ROW_NUMBER и ранги намеренно используют разные порядки.

`WINDOW w AS (...)` даёт имя описанию окна, чтобы не повторять одинаковое выражение для двух функций. Это не таблица и не сохраняемый объект.

## Q02 Три лучших товара каждой категории

CTE ranked_products сначала вычисляет ROW_NUMBER внутри каждой категории. Внешний WHERE оставляет row_num <= 3.

Нельзя отфильтровать оконный номер в WHERE того же SELECT: фильтрация исходных строк происходит раньше оконного расчёта. Внешний запрос видит уже вычисленный столбец CTE.

Обычный LIMIT 3 выбрал бы три товара на весь результат. PARTITION BY и фильтр по номеру дают три в каждой категории. Если товаров меньше трёх, получаем все; пустая категория не даёт ни одной строки. При ничьей по цене выбор определяется меньшим id.

## Общая подготовка дневной выручки в Q03 и Q05

1. day_sales соединяет orders с order_items и оставляет заказы с payments.status = 'completed' через EXISTS.
2. Группировка по дате создания заказа в Europe/Moscow даёт одну строку на день.
3. calendar создаёт непрерывный ряд дат от первого до последнего дня таких продаж.
4. daily присоединяет суммы к календарю. COALESCE заменяет отсутствие продаж нулём.

Без календаря LAG означал бы «предыдущая строка с продажами», а не обязательно вчерашний день. В выбранной реализации пропуски заполняются, поэтому сравнение календарное.

Дата создаётся через `created_at AT TIME ZONE 'Europe/Moscow'`: результат не зависит от TimeZone текущего подключения. Это дата оформления оплаченного заказа. Для отчёта о поступлениях денег пришлось бы отдельно выбрать правило по paid_at, но здесь оно не используется.

Сумма позиций = quantity * unit_price. Текущая products.price может отличаться от цены покупки. Не складываем payments.amount после JOIN с несколькими позициями: такой JOIN повторил бы платёж для каждой позиции.

## Q03 Нарастающий итог

`SUM(day_revenue) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` суммирует выручку с первого дня до текущей строки включительно.

UNBOUNDED PRECEDING — начало раздела, CURRENT ROW — текущая строка. ROWS задаёт рамку по строкам. Здесь на каждый день одна строка, поэтому дневные даты уникальны.

Для дневных сумм 200, 0, 50 итог равен 200, 200, 250. Он не обнуляется в день без продаж. В запросе нет PARTITION BY, поэтому итог общий, а не отдельный по категории или продавцу.

Рамку задаём явно: с ORDER BY стандартная рамка многих оконных агрегатов включает равные ключи текущей строки (RANGE), что может быть неожиданно при неуникальном порядке. В этом отчёте однозначное описание удобнее на защите.

## Q04 Доля продавца в категории

Сначала seller_category_sales группирует оплаченные позиции по двум ключам — category_id и seller_id. Получаем одну сумму на пару категория–продавец.

Далее `SUM(seller_revenue) OVER (PARTITION BY category_id)` добавляет общий оборот категории к каждой такой паре. ORDER BY внутри окна отсутствует: нужна сумма всего раздела, а не нарастающий итог.

Доля = seller_revenue / category_revenue. Для сумм 200 и 50 внутри одной категории знаменатель у обоих равен 250; доли — 0,8 и 0,2, проценты — 80 и 20. Один продавец может иметь разные доли в разных категориях.

NULLIF(category_revenue, 0) превращает нулевой знаменатель в NULL, предотвращая деление на ноль. На текущей схеме цена и количество положительны, так что у реально проданных позиций сумма положительна; защита сохраняет смысл при изменении модели.

В воспроизводимых данных ЛР2 в каждой категории обычно продаёт один магазин, поэтому доли 100% корректны. Проверка с двумя продавцами доказывает, что формула работает и для конкурирующих магазинов. Неокруглённые доли дают в сумме единицу с учётом точности numeric; округлённые проценты могут немного отличаться от 100.

## Q05 LAG и LEAD и изменение выручки

В CTE neighbors:

- LAG(day_revenue) берёт выручку предыдущей строки по day;
- LEAD(day_revenue) берёт следующую;
- из-за непрерывного календаря это соседние календарные дни.

`revenue_growth = day_revenue - prev_day_revenue` — абсолютный прирост к вчера. `growth_pct` — прирост / вчерашняя выручка × 100. NULLIF защищает от нулевой базы.

Для 200, 0, 50:

| День | Выручка | Предыдущая | Следующая | Прирост | Процент |
|---|---:|---:|---:|---:|---:|
| Первый | 200 | NULL | 0 | NULL | NULL |
| Второй | 0 | 200 | 50 | -200 | -100 |
| Третий | 50 | 0 | NULL | 50 | NULL |

Первый LAG и последний LEAD равны NULL, потому что соседа нет. Не заменяем эти NULL нулём: отсутствие наблюдения отличается от нулевой выручки известного дня. После нулевого дня процентный прирост не определён, хотя абсолютный прирост существует.

next_day_growth показывает изменение от текущего дня к следующему, отдельно от прироста к предыдущему.

## Q06 и Q07 Одна задача двумя способами

Задача: рядом с каждым товаром показать среднюю цену категории и отклонение цены от неё.

Q06 использует AVG(price) OVER (PARTITION BY category_id). Все товары остаются, средняя добавляется как столбец. Повторение AVG в выражении отклонения не создаёт новую группу.

Q07 сначала считает среднее обычным GROUP BY в CTE category_averages. На этом шаге детали товара теряются. JOIN возвращает к средним строки товаров, после чего вычисляется такое же отклонение.

Результаты должны совпасть, что проверяется EXCEPT в обе стороны. Оконный способ удобнее, потому что не требует обратного соединения и явно сохраняет детали. Это преимущество читаемости, а не обещание, что оконный вариант всегда быстрее: скорость определяется планом и данными.

Отклонение положительно для товара дороже среднего, отрицательно для более дешёвого и равно нулю при совпадении.

## Q08 Различие ROWS и RANGE

Это дополнительная демонстрация рамок, помогающая объяснить вопросы защиты. Суммируются цены товаров для иллюстрации, а не выручка продаж.

ROWS с порядком price DESC, id накапливает цену по одному товару: для 100, 100, 50 получаются 100, 200, 250.

RANGE с порядком только price DESC включает всех peers — строк с одинаковой ценой текущей группы. Поэтому сразу получаются 200, 200, 250. Id не добавлен в это окно намеренно, чтобы сохранить равенство цен.

Оконный ORDER BY определяет рамку и соседей, а внешний ORDER BY делает вывод стабильным. У первого ROWS результат не означает общую сумму категории; это промежуточное накопление. Для общей суммы надо убрать ORDER BY из OVER либо задать рамку до UNBOUNDED FOLLOWING.
